## What Unsloth actually optimizes

Unsloth doesn't change the fine-tuning *algorithm* — the LoRA math and DPO loss are
identical to what TRL/PEFT compute. What it changes is the low-level execution:

<Mermaid client:visible code={`flowchart LR
  Std["Standard HF: PyTorch autograd, generic CUDA kernels"] --> StdSpeed["Baseline speed/memory"]
  Unsloth["Unsloth: hand-written Triton kernels, manual backprop, no autograd graph overhead"] --> FastSpeed["~2x faster, 50-70% less memory"]`} />

Three specific techniques account for most of the gain:

1. **Custom Triton kernels** for the attention and LoRA forward/backward computations,
   replacing generic PyTorch operations with kernels fused and tuned for exactly the
   shapes fine-tuning uses.
2. **Manual backpropagation** for key operations instead of relying on PyTorch's
   autograd engine, which avoids overhead from building and traversing a generic
   computation graph.
3. **Smarter gradient checkpointing** — Unsloth's `"unsloth"` checkpointing mode offloads
   activations more efficiently than the default, further cutting memory without the
   full recomputation cost of standard gradient checkpointing.

## A realistic QLoRA + DPO Unsloth pipeline

```python
from unsloth import FastLanguageModel
from trl import SFTTrainer, SFTConfig, DPOTrainer, DPOConfig
from datasets import load_dataset

model, tokenizer = FastLanguageModel.from_pretrained(
    model_name="unsloth/Meta-Llama-3.1-8B-Instruct-bnb-4bit",
    max_seq_length=4096,
    load_in_4bit=True,
)

model = FastLanguageModel.get_peft_model(
    model,
    r=16,
    lora_alpha=32,
    target_modules=["q_proj", "k_proj", "v_proj", "o_proj", "gate_proj", "up_proj", "down_proj"],
    use_gradient_checkpointing="unsloth",  # Unsloth's memory-optimized checkpointing mode
)

# Stage 1: SFT
sft_dataset = load_dataset("HuggingFaceH4/no_robots", split="train")
sft_trainer = SFTTrainer(
    model=model,
    train_dataset=sft_dataset,
    args=SFTConfig(output_dir="./sft-out", per_device_train_batch_size=2, num_train_epochs=2),
)
sft_trainer.train()

# Switch to inference-optimized mode isn't needed here — training continues directly into DPO
dpo_dataset = load_dataset("trl-lib/ultrafeedback_binarized", split="train")
dpo_trainer = DPOTrainer(
    model=model,
    train_dataset=dpo_dataset,
    args=DPOConfig(output_dir="./dpo-out", beta=0.1, learning_rate=5e-6),
    processing_class=tokenizer,
)
dpo_trainer.train()

# Save merged model for deployment
model.save_pretrained_merged("./final-merged-model", tokenizer, save_method="merged_16bit")
```

`FastLanguageModel` is a drop-in replacement for `AutoModelForCausalLM` in fine-tuning
contexts — the rest of the TRL pipeline (SFTTrainer, DPOTrainer) is unchanged code,
which is why Unsloth adoption is usually a small diff to an existing training script,
not a rewrite.

## Model support and the trade-off it implies

Unsloth's speedups come from kernels hand-written for specific, popular architectures
(Llama, Mistral, Gemma, Qwen, Phi) — it does not blanket-support arbitrary
`transformers` architectures the way plain PEFT does. In practice this means:

- If you're fine-tuning a mainstream open model, Unsloth almost always "just works" and
  is close to a strictly-better default.
- If you're working with a newer or less common architecture, check Unsloth's supported
  model list before committing a training pipeline to it — falling back to plain
  `transformers`+`peft`+`trl` is the safety net when a model isn't yet supported.

## Free vs. Pro tiers

Unsloth's open-source library supports single-GPU fine-tuning and is what powers most
of its free Colab notebooks. Multi-GPU training is part of Unsloth's paid offering —
teams needing to scale fine-tuning jobs across multiple GPUs should budget for this
rather than assuming the free, open-source path covers it, whereas plain
`transformers`+`accelerate`+`deepspeed` remains fully open for multi-GPU scaling if
that's a hard requirement.
