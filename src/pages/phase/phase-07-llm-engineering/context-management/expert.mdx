## "Context engineering" as the successor discipline to prompt engineering

As agentic systems run longer, multi-step trajectories, the unit of concern shifts
from "one prompt" to "the entire evolving context across an agent's run" — what
Anthropic and others now call **context engineering**: deliberately curating what
occupies the context window at every step of a long-running process, not just what
you write once at the start. This matters because a long-running agent's context is
mostly generated by the agent's *own* prior actions (tool calls, tool results,
intermediate reasoning) — which means context quality degrades unless something is
actively managing it, since nothing about tool outputs is inherently concise or
relevant to future steps.

## Why bigger context windows don't eliminate the problem

It's tempting to treat 1M-token context windows as making context management
obsolete. Empirically this doesn't hold, for two separable reasons:

1. **Positional attention degradation ("lost in the middle").** Even within a
   technically-supported context length, retrieval and reasoning accuracy over
   content in the middle of a long context is measurably worse than over content near
   the beginning or end — a property of how attention is distributed during training,
   not a hard capacity limit. Needle-in-a-haystack benchmarks show this consistently
   across model families, though the severity varies by model and continues to
   improve generation over generation.
2. **Cost and latency scale with tokens processed, not just tokens "available."**
   Every token in the context is reprocessed (modulo caching) on every turn of a
   multi-turn agent loop — a 500K-token context re-sent on every one of 20 agent steps
   is 10M tokens processed, not 500K, if you're not actively trimming/caching between
   steps.

## Context compaction strategies for long agent runs

Beyond simple trimming and summarization, mature agent systems use several
compaction techniques together:

- **Structured note-taking / scratchpad offloading** — the agent writes durable
  findings to an external file or memory store as it works, and the context is
  periodically compacted to just "here's what I've learned so far" plus recent raw
  steps, rather than the full unabridged trajectory. This is the pattern behind
  long-running coding agents that can work for hours without their context ballooning
  linearly with every tool call.
- **Sub-agent isolation** — delegate a bounded sub-task to a separate agent
  invocation with its own fresh, narrow context, and return only the *result* to the
  parent's context, not the sub-agent's full working trace. This trades an extra model
  call for keeping the parent's context focused on orchestration rather than the
  sub-task's raw mechanics (this is the architectural basis for multi-agent
  hand-off patterns — see the Multi-Agent Systems lesson).
- **Selective tool-result retention** — explicitly drop or truncate large tool
  outputs (a full file diff, a large API response) from context once their relevant
  conclusion has been extracted, replacing them with a short derived summary rather
  than carrying the raw payload through every subsequent turn.

## Context rot and its interaction with caching

Aggressively rewriting or reordering context to optimize for relevance directly
conflicts with prompt-caching's requirement of a byte-stable prefix — every edit to
earlier context invalidates the cache from that point forward, forcing full
reprocessing. This is a genuine engineering trade-off, not a solved problem: static,
cache-friendly context (append-only, stable prefix) is cheaper per call but
accumulates staleness and irrelevant volume over a long run; actively curated context
stays lean and relevant but forfeits caching benefits on every edit. Systems handle
this by caching the *stable* prefix (system prompt, tool definitions) while
allowing the *volatile* suffix (recent turns, current task state) to be freely
rewritten — a hybrid, not a single global policy.

## Trade-offs across context management strategies

| Strategy | Context quality over long runs | Caching compatibility | Engineering cost |
|---|---|---|---|
| No management (append everything) | Degrades linearly, eventually breaks | High (fully stable prefix growth) | Lowest |
| Fixed-window trimming | Stable size, loses old detail outright | Breaks cache on every trim | Low |
| Periodic summarization | Stable size, preserves gist | Breaks cache at each summarization point | Medium |
| External scratchpad + compaction | High — durable facts persisted outside context | Preserved for stable prefix portion | High |
| Sub-agent isolation | Highest for orchestrator; sub-agent still bounded internally | Preserved for parent context | Highest — requires multi-agent architecture |

## Evaluating context management quality

The right metric isn't "did it fit" — it's task success rate as a function of run
length. Build evals that specifically stress long-horizon behavior (does accuracy or
tool-call correctness degrade as the agent's step count grows), since context
management failures are often invisible on short, simple test cases and only surface
once a system runs long enough for context degradation to actually manifest — this is
precisely why context-management bugs tend to ship unnoticed until production traffic
generates the long, messy trajectories that expose them.
