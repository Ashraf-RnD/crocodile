## K-quant internals: mixed precision per block

Naive uniform quantization applies the same bit-width to every weight in a
tensor. K-quants instead split each tensor into small fixed-size blocks (commonly
32 or 256 weights) and assign each block its own scale (and often a second-level
"super-block" scale that quantizes the per-block scales themselves), so local
variation in weight distribution is captured much more cheaply than going to a
uniformly higher bit-width everywhere. Within a k-quant scheme like `Q4_K`, not
every block is even quantized identically — the format reserves extra precision
for the more sensitive parts of the model (e.g. attention output and FFN down
projections tend to be treated more carefully than other tensors in several
k-quant configurations), which is a coarser cousin of the "protect the important
weights" idea AWQ formalizes with activation-based salience. The net effect: a
`Q4_K_M` file achieves noticeably better perplexity than a naive round-to-4-bit
scheme at a very similar file size, because the bit budget is spent where it
reduces error most, not spread uniformly.

## Importance-matrix (imatrix) quantization

A further refinement runs a calibration pass — similar in spirit to AWQ/GPTQ's
calibration step — to compute an **importance matrix**: which weights, based on
how they're actually activated on representative text, matter most to the
model's output. Quantizing with an imatrix (`llama-quantize` accepts an
`--imatrix` file, generated by `llama-imatrix` over a calibration corpus) biases
the rounding decisions in each block toward preserving the values that most
affect real outputs, rather than treating every weight in a block as equally
important. This closes much of the accuracy gap at very low bit-widths (3-bit and
below) where plain k-quants start degrading more noticeably — imatrix
quantization is now the de facto standard for anyone publishing low-bit GGUF
quantizations, not an obscure option.

## GGUF vs GPTQ vs AWQ

| Axis | GGUF (k-quant/llama.cpp) | GPTQ | AWQ |
|---|---|---|---|
| Target hardware | CPU, Apple Silicon, consumer/edge GPUs (partial offload) | Data-center/consumer NVIDIA GPUs | Data-center/consumer NVIDIA GPUs |
| Primary runtime | llama.cpp, Ollama, LM Studio | vLLM, TGI, AutoGPTQ/GPTQModel | vLLM, TGI, AutoAWQ |
| File/deployment model | Single self-contained file (weights + tokenizer + metadata) | Weights + separate tokenizer/config files | Weights + separate tokenizer/config files |
| Typical use case | Local/offline inference, edge devices, no GPU required | GPU-server inference, throughput-focused | GPU-server inference, fast quant turnaround |
| Quantization granularity | Per-block (32/256 weights), mixed sub-block precision | Per-column, error-corrected reconstruction | Per-channel scaling + uniform rounding |
| Multi-GPU / tensor-parallel serving | Limited — not the primary design target | Well supported | Well supported |
| Ecosystem tooling maturity | Very broad hobbyist/local ecosystem, growing server use | Mature GPU-serving ecosystem | Mature GPU-serving ecosystem, fastest to (re)produce |

The honest framing: these aren't strictly competing on accuracy so much as on
*where the model runs*. GGUF's design center is "no dedicated GPU, or a modest
one, and you want it to just work" — a CPU-inclusive, single-file, broad-hardware
target. GPTQ and AWQ's design center is GPU-server inference where PagedAttention-style
batching, tensor parallelism, and squeezing the last bit of throughput from a
data-center GPU matter more than single-file portability.

## Edge cases and sharp edges

- **Metadata/architecture drift**: GGUF's format has evolved (older GGML formats
  predate GGUF and aren't compatible); a `.gguf` file built with an older
  llama.cpp version can fail to load in a much newer one if the architecture's
  metadata schema changed — pin llama.cpp/Ollama versions to known-good file
  versions in production-adjacent local deployments.
- **Partial GPU offload nuance**: `-ngl` offloads whole transformer layers to
  GPU, not a smooth continuous trade-off — the memory jump between offloading
  `N` and `N+1` layers is a full layer's worth of VRAM, so tuning it requires
  some trial and error rather than a formula.
- **imatrix calibration domain mismatch**: like AWQ/GPTQ calibration sets, an
  imatrix built from one domain (e.g. English prose) can under-protect weights
  important for another (e.g. code or a different language) — quality claims
  for a specific low-bit GGUF quant should be checked against the calibration
  corpus used, not assumed to generalize.
- **Not a training or fine-tuning format**: GGUF is inference-only; fine-tuning
  workflows still happen in the original framework (PyTorch/safetensors) and get
  converted to GGUF as a final export step, not the other way around.
