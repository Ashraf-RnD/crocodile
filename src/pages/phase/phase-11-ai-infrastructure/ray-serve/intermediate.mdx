## Composing a pipeline with `.bind()`

Real inference services are rarely a single model call — there's preprocessing,
inference, and postprocessing, often as separate concerns you want to scale
independently. Ray Serve deployments compose by binding one deployment's output as
another's input, forming a **deployment graph**:

```python
from ray import serve

@serve.deployment
class Preprocessor:
    def process(self, text: str) -> str:
        return text.strip().lower()

@serve.deployment(ray_actor_options={"num_gpus": 0.5})
class Classifier:
    def __init__(self, preprocessor):
        self.preprocessor = preprocessor
        from transformers import pipeline
        self.model = pipeline("sentiment-analysis")

    async def __call__(self, request):
        data = await request.json()
        cleaned = await self.preprocessor.process.remote(data["text"])
        return self.model(cleaned)

preprocessor = Preprocessor.bind()
app = Classifier.bind(preprocessor)
```

```bash
serve run pipeline:app
```

Each deployment in the graph scales, autoscales, and gets GPU/CPU resources
**independently** — the preprocessor can run on cheap CPU replicas while the
classifier gets GPU replicas, rather than bundling everything into one monolithic
process sized for the most expensive step.

## Autoscaling replicas

Instead of a fixed replica count, `autoscaling_config` lets Ray Serve add/remove
replicas based on load:

```python
@serve.deployment(
    autoscaling_config={
        "min_replicas": 1,
        "max_replicas": 8,
        "target_ongoing_requests": 5,   # scale up once each replica has ~5 in-flight requests
        "upscale_delay_s": 10,
        "downscale_delay_s": 60,
    },
    ray_actor_options={"num_gpus": 1},
)
class LLMDeployment:
    ...
```

`target_ongoing_requests` is the key knob — it's Ray Serve's equivalent of "how much
concurrent work is one replica comfortable handling before we spin up another." Lower
it for latency-sensitive workloads (scale out sooner, keep queues short); raise it for
throughput-optimized batch workloads where some queueing is acceptable. `downscale_delay_s`
being longer than `upscale_delay_s` is a common production pattern — scale up fast
to absorb spikes, scale down slowly to avoid replica thrashing on noisy traffic.

## Fractional GPU allocation for packing multiple models

A single A100 is often more GPU than one small model needs. `num_gpus` accepts
fractional values, letting Ray Serve pack multiple model deployments onto the same
physical GPU:

```python
@serve.deployment(ray_actor_options={"num_gpus": 0.25})
class SmallEmbeddingModel:
    ...

@serve.deployment(ray_actor_options={"num_gpus": 0.5})
class MediumRerankerModel:
    ...
```

Ray schedules both onto the same GPU as long as their fractional requests sum to ≤1
per GPU, which is a meaningful cost lever when you're running several small
models (embedding, reranking, classification) that would each waste most of a
dedicated GPU on their own. The trade-off: Ray doesn't enforce hard memory isolation
between fractional allocations — it's a scheduling hint, not a cgroup-style limit — so
you're responsible for confirming the models' actual memory usage fits together.

## Real production shape

A typical setup: a FastAPI ingress deployment handling auth/validation, `.bind()`-ed
to a preprocessing deployment, `.bind()`-ed to one or more model deployments with
autoscaling and fractional GPU config, all launched together with `serve run` against
a Ray cluster (local for dev, a real multi-node cluster — often on Kubernetes via
KubeRay — for production).
