## System design: two very different request paths

Copilot is really two products sharing infrastructure: **inline completions**
(sub-second, high-volume, low-context) and **Copilot Chat / agent mode**
(multi-second, lower-volume, high-context, tool-using). Designing this system
means designing two different latency/quality trade-offs on the same
platform.

## Context assembly for inline completions

For ghost-text suggestions, the context builder has a strict token budget and
has to decide, in a few milliseconds, what to include:

- The code immediately before and after the cursor (fill-in-the-middle, not
  just "continue from here" — the model needs to produce code that also makes
  sense with what follows).
- A handful of other open files, often ranked by relevance (recently edited,
  same language, imported by the current file).
- Repo-level signal like the language/framework detected, sometimes a small
  set of relevant symbols pulled from a local index — full semantic retrieval
  over a large repo is generally too slow for this path.

```python
# Simplified inline-completion request shape
def build_completion_context(cursor_file, cursor_pos, open_files, token_budget=2000):
    prefix, suffix = split_at_cursor(cursor_file, cursor_pos)
    context = [prefix]
    for f in rank_by_relevance(open_files, cursor_file):
        if remaining_budget(context, token_budget) <= 0:
            break
        context.append(truncate_to_fit(f, token_budget))
    return {"prefix": prefix, "suffix": suffix, "extra_context": context}
```

## Caching is not optional

Because completions fire on nearly every keystroke, a naive implementation
would send a new model request every character you type. Practical systems
**debounce** (wait for a short pause in typing before requesting) and **cache
aggressively** — if you type one more character consistent with the last
suggestion, the previous suggestion can often just be trimmed rather than
regenerated. Prefix caching at the model-serving layer (reusing the computed
attention state for a prompt prefix seen moments ago) also helps, since
consecutive keystrokes share almost the entire prompt.

## Retrieval for chat and agent mode

Copilot Chat and agent-style flows (find this bug, implement this feature)
need context that doesn't fit in a prompt: the whole repository. This is
where retrieval comes in — an index (often embedding-based semantic search
plus traditional code search/symbol lookup) finds the handful of files or
functions actually relevant to the request, which then get inserted into the
prompt alongside the user's message. Agent mode adds another layer: the model
can call tools (read a file, run tests, apply an edit, search the repo) and
loop over the results, which means the system also needs sandboxing and a
budget on how many tool calls a single request is allowed to make.

## Serving considerations

- Inline completions are extremely high-volume and mostly discarded (you keep
  typing past most suggestions), so infrastructure is optimized for **cheap,
  fast, throwaway generations** — small models, aggressive caching, and
  cancellation the instant a new keystroke invalidates the in-flight request.
- Chat/agent requests are lower-volume but each one is more expensive
  (bigger model, retrieval, possibly multiple tool-call round trips), so
  they're routed to separate serving pools rather than competing with
  inline-completion traffic for the same GPUs.
