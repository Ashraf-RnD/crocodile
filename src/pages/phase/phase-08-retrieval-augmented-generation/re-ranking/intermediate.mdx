## Two-stage retrieval: recall cheaply, then rank precisely

Production RAG pipelines rarely trust the top-k from vector (or hybrid) search
directly. Instead they over-fetch a wider candidate set with the fast retriever, then
rerank that set with a slower, more accurate model before truncating to the small
number of chunks actually sent to the LLM:

<Mermaid client:visible code={`flowchart LR
  Q["Query"] --> V["Vector/hybrid search"]
  V --> Wide["Top 50 candidates (fast, approximate)"]
  Wide --> RR["Cross-encoder reranker"]
  RR --> Narrow["Top 5 (slow, precise)"]
  Narrow --> LLM["LLM prompt"]`} />

This decouples two different jobs: the retriever's job is *recall* (don't miss the
relevant chunk, even at the cost of some noise), and the reranker's job is
*precision* (of the chunks that made it this far, put the truly relevant ones first).
Trying to make one model do both well is why single-stage retrieval alone plateaus in
quality.

## Bi-encoders vs. cross-encoders

```python
# Bi-encoder (what powers vector search): encodes query and document SEPARATELY,
# then compares vectors. Fast — precompute document vectors once, reuse for every query.
from sentence_transformers import SentenceTransformer
bi_encoder = SentenceTransformer("all-MiniLM-L6-v2")
doc_vector = bi_encoder.encode(document)   # done once, at indexing time
query_vector = bi_encoder.encode(query)    # done per query
similarity = util.cos_sim(query_vector, doc_vector)

# Cross-encoder (what powers reranking): encodes query and document TOGETHER, letting
# attention layers directly compare tokens across both. Slower — must run per pair, per
# query, no precomputation possible.
from sentence_transformers import CrossEncoder
cross_encoder = CrossEncoder("cross-encoder/ms-marco-MiniLM-L-6-v2")
score = cross_encoder.predict([(query, document)])   # done per query, per candidate
```

The cross-encoder's extra accuracy comes directly from *not* compressing the document
into a fixed vector ahead of time — it can attend across query and document tokens
jointly, capturing interactions a bi-encoder's independent encodings structurally
cannot.

## Using a hosted reranking API

Running cross-encoders yourself works, but hosted rerankers (Cohere, Voyage, Jina) are
common in production because they're tuned on large-scale relevance data and require
no GPU management:

```python
import cohere

co = cohere.Client(api_key="...")

response = co.rerank(
    model="rerank-english-v3.0",
    query="How do I cancel my subscription?",
    documents=[c.text for c in candidates],  # your top-50 from vector search
    top_n=5,
)
for result in response.results:
    print(result.relevance_score, candidates[result.index].text)
```

## Reranking inside a LangChain retriever

```python
from langchain.retrievers import ContextualCompressionRetriever
from langchain.retrievers.document_compressors import CohereRerank

base_retriever = vectorstore.as_retriever(search_kwargs={"k": 50})
compressor = CohereRerank(model="rerank-english-v3.0", top_n=5)

retriever = ContextualCompressionRetriever(
    base_compressor=compressor,
    base_retriever=base_retriever,
)
top_chunks = retriever.invoke("How do I cancel my subscription?")
```

`ContextualCompressionRetriever` wraps a base retriever transparently — the reranking
step slots into an existing RAG chain without restructuring the rest of the pipeline.

## The latency and cost you're trading for accuracy

Reranking adds a real cost: one model call per (query, candidate) pair, so reranking
50 candidates means 50 scoring operations per query, on top of the initial retrieval
call. This is why reranking always operates on a *narrowed* candidate set (dozens, not
thousands) — the accuracy gain from reranking is worth paying for on a small
shortlist, but would be prohibitively slow and expensive applied to an entire corpus,
which is exactly why it's a second stage rather than a replacement for vector search.
